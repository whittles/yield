## Design Specificity Verdict

**Partially authored: a genuinely domain-specific product wearing an interchangeable SaaS chassis.** The words and the arithmetic are unmistakably woodworking. The composition, chrome, and typography are not.

**Authored, and worth protecting:** per-condition allowances for rough / skip-planed / S3S / S4S (`project.js:14-19`); kerf and per-face planing allowance; the snipe buffer with a plain-English scale (`ResawView.vue:97`); "jointed face against fence" (`:731`); "stop block recommended, not a fence" (`:704`); "no glue needed (allows wood movement)" (`BinView.vue:386`); "nominal ½" plywood is typically 15/32"" (`BinView.vue:85`). Fraction-first input as the primary contract — dimensions live as strings and round-trip through `parseFraction`/`formatFraction` — is the most product-specific interaction decision in the app, and it is correct. The resaw cross-section palette (`#e8d5b0` / `#d4a84b` / `#8B6914`) is authored end-grain tan-and-gold, not chart defaults.

**Generic — swap the logo and it's a billing dashboard:** the `#242833` bar + brand block + four underline tabs + `max-w-5xl` centered white cards (`App.vue:5-98`). The 4-tile KPI row (`ResultsSummary.vue:1-42`) is the canonical analytics tile, measuring lumber but composed like MRR. Typography does no work — Assistant at 12/14/16px for essentially everything, and **dimensions render smaller and lighter than their own labels** (`CutPlanTable.vue:48`). Emoji as the entire icon system (📐 🪵 📦 ⚠️ ✂ ℹ️ 🖨 ⬆ ⬇ ↺). The FAB is Material Design with an off-palette indigo hover that exists nowhere in `tailwind.config.js`.

**Missed opportunities for product character:** grain direction is never drawn even though the solver knows about it (`BinView.vue:539-540` comments `// no rotation — keep grain direction consistent`). Waste is inert grey hatch filling the whole board rect, so the most emotionally loaded quantity in the product isn't even a pointable region. No offcut identity — the app reports 84% waste but never names the usable piece you'd keep. No cut sequence in the flagship: the Yield plan groups by part, while real work groups by machine setup (ResawView understands this; YieldPlannerView does not). And `CutDiagram.vue:93` silently distorts board aspect ratio via `Math.min(MAX_H, …)` — a diagram you cross-reference against a physical board must not lie about proportion.

## Overall Impression

The domain thinking here is better than the interface wrapped around it. Someone who has actually milled lumber wrote this — the allowance model, the machine-order instructions, the fraction-first input, the versioned print sheet are all specific and correct in ways you cannot fake. Then that substance is presented through generic dashboard chrome that buries it: the cut diagram is fourth in visual weight behind four KPI tiles and two banners, and the finished dimension — the single number a woodworker acts on — is the faintest text on both screen and paper.

The biggest opportunity is not a restyle. It is deciding that **the plan is the product** and rebuilding the results view around the artifact a person carries to the saw: the diagram large and honest, the dimension bold, the cuts sequenced by machine setup, the offcuts named. Everything else is accounting that belongs after it.

## What's Working

1. **The milling-order model** (`ResawView.vue:699-811`, `CutPlanTable.vue:36-45`). Instructions follow real machine sequence — miter → jointer → bandsaw → drum sander → miter → table saw → hand plane → sander — and state the allowance arithmetic inline ("Resaw to **7/8"** → plane to **3/4"**"), so a skeptical woodworker can *audit* the number instead of trusting it. That is the correct trust posture when the next action is irreversible.
2. **Fractions as the primary input contract.** `fractions.js` plus string-typed dimensions in the store means the app never forces decimal conversion and echoes fractions back — and the hint lives at the point of use (`StockTable.vue:192-194`), not in a help page. Unglamorous and exactly right for the domain.
3. **The Yield print header is a real document** (`YieldPlannerView.vue:36-131`) — logo, tool name, date, **version stamp**, disclaimer, with explicit print-safe inline styles rather than betting on Tailwind surviving `@media print`. Versioning a shop sheet so you can tell which plan is taped to the wall is a specific, thoughtful decision. Print holds up structurally: 0 clipped elements, `no-print` correctly hides 12/12, 16/16, 6/6.
4. **Responsive containment is solid** — zero page-level overflow at any tested width, which is rarer than it sounds for an app this table-heavy.

## Priority Issues

### [P0] The flagship tool is unreachable from its own tab
`App.vue:64` pushes `/`; `main.js:10` maps `/` to HomeView; `App.vue:143` labels `/` as `'home'`. Verified live: clicking "Yield Planner" gives `url=#/`, `h1="Woodworking Calculators"`, highlighted tab "Home". Because `activeTab` never returns `'yield'` for any reachable path, that tab can never light up. Only the Home card reaches `/yield`.
**Why it matters:** the tab bar is the obvious first tap, especially on a phone. The user lands on the wrong page with the wrong tab lit and no explanation.
**Fix:** `App.vue:64` → `router.push('/yield')`; drop `route.path === '/'` from the home branch at `:143`; add `{ path: '/', redirect: '/yield' }` in `main.js`.
**Suggested command:** `/impeccable harden`

### [P0] Invalid dimensions are accepted, then parts silently vanish from the plan
`fractions.js:11` routes `-5` through `parseFloat` and returns it, while `:14` rejects negatives in fraction form. `:19` divides with no zero check, so `1/0` → `Infinity`, and `formatFraction(Infinity)` returns the string `"Infinity"` — which can reach a printed dimension. `abc` and emoji → `0`. Qty `-3` accepted despite `min="1"`. All four accepted with no field marking and no message — then Calculate reports **"Parts Placed 2 / 2"**, because the dropped parts left the denominator too.
**Why it matters:** a stray keystroke removes a quarter of the project from the cut sheet, and the summary tile *confirms* everything was placed. The user drives to the shop with an incomplete plan and full confidence. This is the most dangerous defect in the app.
**Fix:** validate on blur — reject non-positive and non-finite values, mark the field `aria-invalid` with a visible message, and make `calculate()` surface a blocking "3 parts have invalid dimensions" panel instead of silently filtering.
**Suggested command:** `/impeccable harden`

### [P0] Box Planner: print throws, and all its state is disposable
`BinView.vue:398` binds `@click="window.print()"`. `window` is not in Vue's template global allowlist, so it compiles to `_ctx.window.print()` → `Cannot read properties of undefined (reading 'print')`. The other two views correctly wrap it in a script function (`YieldPlannerView.vue:323`, `ResawView.vue:1091`) — verified. Separately, Bin inputs are local `ref`s (`BinView.vue:418-426`) instead of store state, so they are excluded from localStorage, from Export (`export.js:5-13`), and from Reset — verified: a typed `30` reverted to `12` after reload, while `99` survived a Reset.
**Why it matters:** print *is* the Box Planner's deliverable, and it is 100% dead. And a woodworker who dimensioned a bin, walked to the shop, and came back has lost the work.
**Fix:** add `function printSheet() { window.print() }` and bind it. Move Bin inputs into `project.js` alongside `resawStock` so they inherit persistence, Export, and Reset.
**Suggested command:** `/impeccable harden`

### [P0] Every dimension on the Box Planner shows a doubled inch mark
`binSolver.js:12,16` already append `"`; `BinView.vue` appends another at `:19-20, 158, 165, 172, 204-205, 222, 277, 280, 302, 304, 328, 362, 377-379`. Verified. Result throughout: `12""`, `14 13/16"" × 29""`, `6 1/4""`.
**Why it matters:** `12""` off a printed sheet forces the reader to decide whether it's a typo or feet-and-inches. On a cut list that is the whole document, it undermines every number on the page.
**Fix:** one owner for the unit mark — strip it from the templates, or strip it from `formatIn` and keep it in templates. Consistently.
**Suggested command:** `/impeccable clarify`

### [P1] The shipped default state demonstrates failure
`project.js:23-39`: one 96×8×1½ skip-planed board → 1 3/8" usable thickness, against parts including four Legs at 1½" thick. Geometrically impossible. A new user's very first click yields `2 / 6` parts placed, **84% waste in red**, 16% yield in red, and "4 parts could not be placed — **insufficient stock**" (`YieldPlannerView.vue:152`) — which is also a *misdiagnosis*, since no quantity of that stock could ever hold a 1½" part milled from a 1 3/8" board.
**Why it matters:** the peak-end rule says the first run sets the impression. This one says "this tool doesn't work" and then explains why incorrectly.
**Fix:** ship defaults that produce a good plan, and distinguish "won't fit in any single board" from "ran out of stock."
**Suggested command:** `/impeccable onboard`

### [P1] Print buries the plan, drops page numbers, and hides the dimension
Three compounding faults on the product's most important surface. `print-break-before` on each board card (`YieldPlannerView.vue:165`) makes page 1 the bf accounting tables and page 2 the first board — a 6-board plan prints 7 pages, ordered wrong. `style.css:77-99` puts "Page N of M" and the URL in `@page` margin boxes, **which Blink does not implement**, while `:102` hides the in-flow `.print-footer` fallback — verified: no page numbers on any page. And `Final Size` is `text-text-muted font-mono text-xs` (`CutPlanTable.vue:48`), the smallest lightest text on the sheet, while procedural prose is darker and larger. No tick-off column.
**Why it matters:** a woodworker cross-referencing an unnumbered 7-page stack, hunting for a faint 10pt grey dimension under shop light with sawdust on their hands, will mis-read a cut. This is the exact scene the product exists for.
**Fix:** board sheets first, accounting last; make `Final Size` the boldest cell on the row; restore a real in-flow print footer with page numbers; add a `☐` column per cut row.
**Suggested command:** `/impeccable layout`

### [P1] Results go stale silently, and mobile results are unusable
`store.results` (`project.js:41`) is never invalidated when inputs change and is never persisted — so editing a length after Calculate leaves the old diagram and old dimensions on screen looking authoritative, and a reload wipes the plan while keeping the inputs. Meanwhile `CutPlanTable.vue` has **no responsive treatment at all**, unlike `StockTable.vue:10-77` and `PartsTable.vue:10-58` which both ship `sm:hidden` card views: at 390px the Steps column wraps to 5 lines per step and the Print FAB sits on top of it, while CutDiagram renders ~30px tall with illegible labels. Resaw needs 6,200px of scroll before its Calculate button, with no sticky CTA.
**Why it matters:** the phone in the shop is the real device. The failure mode is: tweak a length, glance at the unchanged diagram, cut.
**Fix:** `watch` inputs to mark results stale ("Inputs changed — recalculate") and persist `results`; give `CutPlanTable` a mobile card layout with the final dimension as the headline; raise the diagram's mobile height with a numbered legend; add a sticky Calculate on Resaw.
**Suggested command:** `/impeccable adapt`

### [P1] The app is effectively unusable with assistive tech
61 of 61 form controls unlabeled; 14 tables with no `th[scope]` and no caption; all 8 SVG diagrams with no accessible name, not hidden and not described; `nav: 0` with the tab bar as bare buttons conveying state visually only; no `<h1>` on the flagship (outline starts at `h2`); zero `aria-live` regions so Calculate announces nothing; yield/waste severity encoded by color alone (`text-success`/`warning`/`danger`), making 16% and 84% identical to a screen-reader or red-green colorblind user; `text-muted #6b7280` failing AA on both warm backgrounds; and at 200% zoom the Label column has no `min-width`, clipping "Board 1" to "Bo".
**Why it matters:** this is a free public tool. Right now a screen-reader user hears "edit text, blank" forty times and gets nothing from the diagram that is the entire output.
**Fix:** label every control; add `scope` to `th`; give each SVG a `<title>`/`<desc>` or a text-equivalent table; wrap the tab bar in `<nav>` with `aria-current`; add an `h1`; add a polite live region on Calculate; pair every color-coded status with text or an icon; darken `text-muted` to ~`#5b6472`.
**Suggested command:** `/impeccable audit`

### [P2] Malformed import bricks the app with no message
`JSON.parse` failure alerts (`export.js:41-42`), but *valid* JSON with wrong shapes is accepted unchecked by `loadProject` (`project.js:97-114`). `{ stock: "not-an-array" }` → `store.stock.reduce is not a function` → the debounced watcher **persists the broken state** → after reload the page renders header and footer only, 174 characters of body text, no error, no explanation. Reset still works; nothing on screen says so.
**Fix:** validate shape in `loadProject` before assigning; wrap hydration in a try/catch that clears the key and shows a recoverable error.
**Suggested command:** `/impeccable harden`

## Questions to Consider

1. If the diagram can't tell a woodworker where to put the tape measure — no offsets, no cut numbers, no grain axis — is it a diagram or decoration? What would it take for the *printed* diagram to be sufficient on its own, with the table as backup rather than the reverse?
2. The Resaw Planner organizes output by machine; the Yield Planner organizes it by part. One of those matches how the work actually happens. Why does the flagship use the other one?
3. What is the offcut worth? If the primary output were "here are your parts, and here are the three usable offcuts you'll have left," would waste percentage still need two of four headline tiles?
4. The shipped defaults produce a geometrically impossible plan. What *is* the ideal first-run state — a working example, an empty state that teaches the input model, or a "what are you building?" preset?
5. The user is standing at a saw holding a phone. Should the results view be a scrollable document at all — or one cut per card, advanced with a thumb and ticked off, with the printed sheet as the archival format?
